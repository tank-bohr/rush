# Two type systems, one Ruby interpreter: Steep vs Sorbet under extreme quality pressure

## Abstract

What happens when the same non-trivial Ruby program is checked independently by both
[RBS](https://github.com/ruby/rbs)/[Steep](https://steep-lang.org/) and
[Sorbet](https://sorbet.org/), while coverage, on-demand mutation testing, complexity ratchets,
code-smell checks, and differential behaviour tests are all allowed to veto the resulting design?

rush is a useful experiment because its subject is difficult but its correctness is unusually
observable: it is a pure-Ruby POSIX `sh`, checked against
[POSIX.1-2017](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) and differentially
against `dash`. The code includes a lexer, a Racc parser, recursive ASTs, process boundaries,
file descriptors, signals, job control, dynamic dispatch tables, and native calls through
Fiddle. This is not a CRUD application selected to make gradual typing look easy.

The short result is:

- **Steep became rush's more detailed static domain model.** Its external RBS described recursive
  unions, literal-symbol protocols, tuple boundaries, and structural interfaces while reducing
  its receiver-based untyped ledger to zero at a historical milestone. This describes the model
  built in rush; it is not a comparison of the tools' incompatible percentages.
- **Sorbet supplied the more disruptive second opinion.** Its inline model and nominal runtime
  checks found different class-shape, dispatch, Boolean-return, and call-boundary problems. It
  also imposed a real production cost: runtime call wrappers more than doubled the measured time
  of the interpreter workloads.
- **The combination was more valuable than either score.** The checkers disagreed in concrete,
  useful places. Their intersection selected better class shapes, exposed library-signature
  defects on both sides, and forced hidden invariants either into the design or into an explicit
  boundary ledger.
- **The surrounding gates determined whether a type fix was acceptable.** Coverage rejected fake
  nil branches, reek rejected misplaced narrowing work, RuboCop sometimes had to yield to typed
  Ruby, Mutant separated behavioural proof from type ceremony, and the `dash` corpus prevented a
  cleaner type shape from silently changing shell semantics.

This is a report about that interaction, not a claim that two type systems should be a normal
production default.

## The experiment

Both checkers run in the default gate over the same implementation (Steep checks `lib/`;
Sorbet checks `lib/`, `exe/`, and its configured RBI shims, so their scopes are not identical):

```text
compile (Racc) → { RuboCop, reek, flay, flog, Steep, Sorbet, parallel RSpec }
```

Steep reads external declarations under [`sig/`](../sig) through
[`Steepfile`](../Steepfile). Sorbet reads inline `sig {}` blocks and the small RBI surface under
[`sorbet/rbi/`](../sorbet/rbi) through [`sorbet/config`](../sorbet/config). The
[`Rakefile`](../Rakefile) invokes the raw `sorbet-static` binary rather than `srb tc`, because the
wrapper auto-loaded a self-inconsistent RBI shipped by another gem before rush's source was even
read.

Mutant is intentionally absent from that diagram: it is a slow, on-demand 95% subject/full-project
ratchet, whereas flay and flog run in the default gate. Flog was part of the veto surface throughout
this study but produced no distinct type-system episode worth manufacturing into one.

The two signature sets are deliberately independent. They are not generated from one another.
That matters: generating one from the other would produce two parsers for one assertion, not two
models capable of disagreeing.

Inline Sorbet syntax still appears in the Ruby source Steep checks. The small
[`sig/sorbet_dsl.rbs`](../sig/sorbet_dsl.rbs) bridge therefore teaches Steep only enough about
`T::Sig` to parse the DSL. In particular, the `sig` block gets a concrete
`T::Private::DeclBuilder` self type so calls such as `params`, `returns`, and `void` resolve, while
the Sorbet type expressions inside the block remain opaque to Steep. `T.let` and `T.must` are the
narrow exceptions: their bridge signatures preserve or narrow the value type so a Sorbet helper
inside a real expression does not turn a Steep-typed call chain into `untyped`.

That bridge is infrastructure, but it also states the experimental contract: **same Ruby, two
independent interpretations**.

This remains a longitudinal case study of one AST-heavy application and one Ruby/toolchain line,
not a controlled benchmark of the products. Steep landed first, so Sorbet encountered code already
reshaped by Steep; its marginal cost and findings are necessarily path-dependent.

## How the rollout changed the result

The first Steep baseline used RBS generated by `rbs prototype rb`. It was green, but mostly
`untyped`: 108 of 122 files were checked, 14 were ignored, and approximately 54% of calls had typed
receivers. That was a bootstrapping result, not evidence of safety.

The useful work came from tightening the graph from its high-fan-out points:

1. value objects and tables;
2. `Executor`, `ShellState`, and `SystemCalls` — the execution spine;
3. builtin base classes and I/O;
4. AST members and recursive arithmetic nodes;
5. lexer and expansion collaborators;
6. runners and parser boundaries.

Typing `Executor` alone moved Steep's project call coverage from 57.7% to 63.1%; typing the builtin
base and `IoTable` moved it from 64.5% to 72.2%. The lesson was architectural: annotate the
collaborator through which many calls flow, not whichever low-percentage file happens to be at the
bottom of the report.

The late ledger shows why percentages were still useful when treated as a search instrument:

| Milestone | Commit | Steep typed calls |
| --- | --- | ---: |
| Initial prototype baseline | [`335eca4`](https://github.com/tank-bohr/rush/commit/335eca4f5421148e32520e784d7dbd95f6a668d8) | about 54% |
| Typed runner/arithmetic/builtin pass | [`1a0288d`](https://github.com/tank-bohr/rush/commit/1a0288d0abd99cf759e40033ecc15a3d163a547f) | about 93% |
| Untyped-receiver sweep | [`467ba6b`](https://github.com/tank-bohr/rush/commit/467ba6b2234a2d0d284ce8570d9a85776a0b7540) | 8,973 / 8,984 (99.88%) |
| Racc boundary named | [`afaa06b`](https://github.com/tank-bohr/rush/commit/afaa06b729416c53ff61030ea1f418ebfc87207e) | 9,007 / 9,010 (99.97%) |
| Token vocabulary added | [`9e76ed1`](https://github.com/tank-bohr/rush/commit/9e76ed10ccfd29a748fbb6adc000e11af665776c) | 9,008 / 9,008 (100%) |

The last step was not achieved by declaring the remainder harmless. The lexer/parser seam's
`[untyped, untyped]` token pair became explicit RBS aliases for token kind, value, and tuple shape.
That made the final Racc error lookahead typeable and also exposed a **latent, grammar-unreachable
hazard**, not a demonstrated user-visible bug: a heredoc delimiter was being classified before use,
so an assignment-shaped value could reach code expecting a word with segments. The structural
repair — take an awaited delimiter before classification — matched `dash`'s token order and
removed the bad state instead of casting it away.

After Steep's initial rollout, Sorbet bootstrapped from `# typed: false`, which mostly checked
syntax and constants, to `# typed: true`; Steep's 99.88→100% tail happened later. Raising the sigil
across the initial source produced only 22 errors, but those
errors were concentrated at genuine seams: generated Racc methods, non-static splats, Kernel
methods on module singleton self, and incorrect standard-library RBI return types. Inline
signatures were then rolled out by cluster.

The two tools do not publish comparable coverage metrics. Steep counts a call as untyped when its
**receiver** is untyped. Sorbet's `--track-untyped --counters` reports typed and untyped **sends**
over a different input set, including configured RBI files. Comparing the percentages as a race
would be false precision.

For scale, a 2026-07-12 snapshot (parent revision `327c081`; Steep 2.0.0, RBS 4.0.3,
Sorbet/Sorbet Runtime 0.6.13320) contained:

- 198 Ruby library files: 192 at `# typed: true`, 5 at `# typed: false`, plus the generated parser
  with no sigil; `exe/rush` is a separate `# typed: true` file;
- 202 RBS files, 7,801 lines in total;
- 1,504 inline `sig` declarations in production Ruby;
- one Steep ignore, the Racc-generated parser;
- Steep: 10,812 / 10,830 typed calls (99.83%); the 18 current untyped calls are contained in the
  parameter-form lambda registry and the Fiddle collation boundary;
- Sorbet: 10,598 / 11,891 typed sends (89.13%) in its counter scope, with 1,618 signatures including
  configured RBI declarations.

`steep check` passes at this snapshot, but `steep stats` also emits one internal compatibility
`ERROR` while calculating `Rush::Status`; the aggregate is useful, not warning-free. This is another
reason to preserve the diagnostic stream beside the exit status.

These counts measure declaration footprint and checker friction, not total engineering cost: the
rollout's person-hours and comparative static-gate runtime were not instrumented.

The historic 100% milestone is therefore a milestone, not a timeless badge. Later features added a
native Fiddle boundary and richer quote-aware parameter parts. The current ledger names them rather
than preserving 100% by hiding new code.

## What Steep caught — and what it cost

### 1. Hidden invariants in ordinary Ruby containers

Much of the early work was nilability: `Array#last`, `Array#pop`, `String#[]`, regex captures, and
`Process::Status#termsig` all honestly return optional values in their library signatures, while
rush knew more from local control flow.

The cheap response is a coercion:

- `fetch(-1)` is loud: if the invariant fails, it raises;
- `to_s` and `to_a` are silent: they convert a violated invariant into plausible empty data.

Steep made that distinction visible. An audit found no existing masked bug, but it changed the
preferred design. `IfsScanner`, for example, stopped finding an implicit current field through
`@fields.last` and gained a dedicated `@current` object that always exists by construction. The
checker no longer needed persuasion because the object model now carried the invariant.

This was one of the strongest results of the experiment: **structure beats coercion**. A type
checker is most valuable when it causes an invariant to become true by construction, not when it
adds a cast explaining why the old shape is probably fine.

### 2. Recursive and protocol-shaped domain models

RBS expressed recursive arithmetic-node unions, heterogeneous token tuples, literal symbol unions,
and structural stream interfaces naturally. Abstract base declarations also captured protocols that
Ruby code enforced only by convention. `CommandLookup::Match`, for example, gained base
`describe`/`terse` methods once callers were typed against the base rather than whichever subclass
happened to flow through a guard.

Steep's own metric supplied a useful mental model: an untyped return value does not necessarily make
a call untyped; an untyped receiver does. A dynamic `send` in the old `test` evaluator was not the
largest problem. The untyped argument and collaborator plumbing around it was. That reframing made
the tail tractable.

### 3. Library model failures can silently erase checking

The worst Steep finding was about Steep itself. rush carried an extension for `StringScanner`. When
RBS 4.0.3 later shipped some of the same methods, the extension created an
`RBS::DuplicatedMethodDefinitionError`. `steep check` did not fail or clearly report it; the whole
`StringScanner` class silently became `untyped`. A deliberately nonexistent scanner method then
passed the checker.

The repair in [`sig/strscan_ext.rbs`](../sig/strscan_ext.rbs) appends only the missing String-pattern
overloads with RBS's `| ...` syntax. Restoring the class immediately found a real rush gap in printf
template capture narrowing.

The operational lesson is severe: a green gradual-type command is not enough. Track untyped calls,
inspect fatal/internal diagnostics, and probe important library classes with a known-invalid call.
A broken shim can remove more checking than a visible source error.

### 4. Steep-specific friction

Steep 2.0.0 also imposed costs that were not code findings:

- `Data.define` blocks with methods could crash or attribute instance methods to the enclosing
  module when the prototype RBS declared the constant as `untyped`.
- It did not propagate a frozen hash's expected callable type into lambda parameters. Operator
  registries needed a `#:` annotation on each lambda even though the constant had a precise RBS
  value type.
- narrowing worked for a local variable but not for two calls to the same nilable method;
- RBS core placed `spawn`, `exec`, `fork`, and `exit!` on `Kernel`, not the `Process` singleton used
  by the source, requiring an augmentation;
- the generated Racc parser remained outside the checked implementation and needed a hand-written
  boundary declaration.

External RBS kept the Ruby implementation visually cleaner than inline signatures, but it created a
second tree large enough to drift. The 7,801 current RBS lines are not free documentation; they are
another maintained program.

## What Sorbet caught — and what it cost

### 1. A second model selected a better `Data` class shape

The clearest cross-checker result was a three-way disagreement:

- `class X < Data.define(:a)` let Steep attribute methods correctly, but Sorbet rejected the
  non-literal superclass expression;
- `X = Data.define(:a) do ... end` satisfied Sorbet, but Steep could not type the block's instance
  methods;
- `X = Data.define(:a)` followed by `class X ... end` satisfied both.

The third form became the shared design. Neither checker merely duplicated the other; their
constraints intersected at a representation that made the generated value class and its methods
explicit.

Later, some generated-adjacent arithmetic payloads became ordinary typed Ruby classes instead. That
was an even stronger version of the same result: where metaprogrammed readers obscured invariants to
both systems, straightforward state won.

### 2. Inline checks attacked dispatch and return-shape seams

Sorbet rejected the non-static `send(sym, *args)` shape in `test`, which helped replace symbol-based
operator dispatch with typed lambdas and a pattern match over the POSIX arity rules. It also forced
Boolean APIs to return actual Booleans rather than Ruby's common `x && y` result, whose false case may
be `nil`. Those changes were observable at Sorbet runtime even when Steep was satisfied statically.

Literal-symbol narrowing exposed another difference. Steep could narrow `AST::List | :eof` after an
`== :eof` check; Sorbet widened the literal to `Symbol`, requiring a small `T.cast` at the remaining
branch. Conversely, Sorbet's restrictions on loop-variable type changes made status initialization
explicit with `T.let` once `Status.success` acquired a signature.

These were not all wins for Sorbet. They were useful disagreements: each showed where one checker's
flow model was stronger or stricter than the other's.

### 3. Runtime validation is a distinct capability

Sorbet's inline signatures can validate calls at runtime. Steep cannot: RBS is static metadata. A
bad `Status.new("x")` therefore fails at runtime under Sorbet.

That nominal checking also rejected RSpec verifying doubles which implemented the required
`Process::Status` interface but were not instances of the declared class. The suite keeps static
checking and installs a call-validation error handler for those doubles. A closed-file-descriptor
sentinel similarly forced a Sorbet return signature to remain looser than Steep's structural `IO`
model.

Runtime validation was thus both stronger and more coupled to concrete runtime classes. Whether that
is a benefit depends on the boundary.

### 4. Sorbet's library models were not uniformly better

The second checker found drift partly by being wrong in different ways:

- its `Integer(value, exception: false)` model was non-nil, making the real nil fallback appear dead;
- `File.writable?` was typed as `T.nilable(Integer)` even though it returns a Boolean;
- bundled `StringScanner` declarations were too loose for rush's scanner boundaries;
- the `srb` wrapper loaded an unrelated Prism RBI that referred to a removed constant.

Sometimes the mismatch still improved the source. Arithmetic parsing moved from
`Integer(..., exception: false)` plus a nil fallback to the raising form plus an `ArgumentError`
translation, which both tools understood and which made failure control flow explicit. In other
places, `!!` or a focused RBI shim was simply the price of an inaccurate ecosystem model.

The value of two checkers was not that one had the authoritative standard library. It was that their
failures were unlikely to line up.

### 5. Inline signatures have source and runtime weight

At the first full rollout, roughly 690 `sig` blocks covered 110 classes. The current source has 1,504
production declarations. That ceremony affected tools which were never designed to distinguish
annotations from executable logic:

- class-length metrics counted signature lines;
- named block parameters were required because signatures refer to them, conflicting with
  RuboCop's anonymous-forwarding preference;
- flay attributed 712 of 906 duplication-mass points to structurally identical generic `sig`
  blocks.

The project changed the metrics rather than pretending declarations were logic.
[`tasks/complexity.rake`](../tasks/complexity.rake) filters `sig` AST nodes before flay analyzes
structural duplication, and RuboCop is configured for explicit block forwarding. Once signature
noise was removed, flay exposed a real duplicated option-cluster parser that had been hidden below
the inflated threshold.

The larger cost was runtime. Profiling the canonical 10,000-iteration shell loop with Sorbet call
validation enabled put `UnboundMethod#bind_call` on 96.2% of sampled stacks. Disabling wrappers
changed the five-sample medians from:

| Workload | Runtime checks on | Runtime checks off | Change |
| --- | ---: | ---: | ---: |
| Startup | 130.553 ms | 124.553 ms | 1.05× faster |
| while/arithmetic | 3,950.087 ms | 1,771.277 ms | 2.23× faster |
| expansion-heavy | 2,772.894 ms | 1,351.353 ms | 2.05× faster |

These were five-sample medians on the same x86_64 Linux/i9-11900K host under Ruby 4.0.5; they
apply to the committed rush workloads, not Ruby applications in general.

The executable now calls [`Rush::RuntimeTypeChecks.configure`](../lib/rush/runtime_type_checks.rb)
before loading rush and defaults Sorbet's checked level to `:never`.
`RUSH_RUNTIME_TYPECHECKS=1` restores `:always` for diagnosis. Library use and the test process keep
runtime validation; both static gates remain unchanged.

That policy is specific to an interpreter's very hot dispatch path, but the general lesson is not:
**measure runtime signatures as runtime code**.

## What the other gates did to the type-driven design

### Coverage rejected fictional safety branches

A common Steep error was “this value may be nil” where the domain guaranteed presence. Adding
`return unless value` makes the checker happy, but it also invents behaviour for a state that should
not exist. Under meaningful branch-coverage pressure, that branch either remains uncovered or gets
a contrived test which blesses an impossible state.

This happened concretely in `Status.of`: absent `exitstatus` implies present `termsig`, but Steep
could not correlate the two accessors. A nil guard would have added an unreachable branch; the code
used the branchless `termsig.to_i` on the signalled path. Scope-frame reads similarly use loud
`fetch(-1)` where begin/end pairing guarantees a frame. For the more load-bearing `IfsScanner`
invariant, the earlier `@current` refactor removed optionality structurally.

rush therefore preferred, in order:

1. a structural model which makes the value non-optional;
2. a loud operation such as `fetch` which preserves invariant failure;
3. a behaviour-preserving coercion only where the domain proof is strong and documented;
4. an actual guard only when absence is part of the API.

Coverage did not compete with typing here. It prevented typing from weakening the design with fake
recovery paths.

### reek and RuboCop tested placement and readability

A Steep-friendly rewrite made `TestExpr#evaluate` call
`binary(args[0], args[1], args[2])`; the extra `args` references tripped reek's `FeatureEnvy`.
Passing the array once and destructuring inside `binary` satisfied both tools and put the data work
in the method which owned it.

Not every conflict had a common form. RuboCop's `Style/SymbolProc` required `lambda(&:-@)` in an
operator table, while Steep could not reconcile the resulting callable arity. Explicit lambdas were
clearer and typeable, so the cop was scope-disabled for that file. `Style/DataInheritance` likewise
preferred the `Data.define` block form Steep could not model and had to yield.

The useful rule was not “all gates must always agree.” It was “a suppression must identify which
tool is mis-modeling this exact Ruby shape.”

### Mutant distinguished behavioural proof from type ceremony

Mutation testing and typing answer different questions. In the concrete
`rake mutant:check[Rush::Lexer*,95.0]` run, the subject reached 98.46%, while the 53 documented
survivors included `T.let` generic noise and `T.must` under
the suite's validation policy alongside ordinary equivalent/defensive branches. Mutations which
remove those type helpers often survive because they do not change successful runtime behaviour;
forcing a behavioural spec to kill each one would test annotation implementation details. rush's
Mutant investigations therefore catalogued these as type-ceremony equivalents instead of weakening
type precision or writing artificial tests.

Conversely, when typing changed executable structure — replacing dynamic dispatch, introducing a
current-field object, taking heredoc delimiters before classification — mutation and differential
tests still had to prove the behaviour. Types constrained the state space; Mutant assessed whether
assertions observed meaningful changes; the `dash` corpus checked the externally defined shell
result. No one score substituted for the others.

This separation also explains why the test suite's Sorbet runtime error handler is acceptable for
RSpec doubles: static Sorbet checks the declared calls, verifying doubles check the interface used by
tests, and Mutant checks observable behaviour. Requiring a mock to satisfy Sorbet's nominal
`is_a?` test would not add a fourth independent proof.

The examples above intentionally separate five categories: (1) real execution or call-contract
findings, such as strict Boolean returns; (2) latent hazards, such as the grammar-unreachable heredoc
shape; (3) design improvements, such as `IfsScanner` and `Data.define`; (4) checker limitations, such
as inference gaps; and (5) bad standard-library signatures. Collapsing all five into “bugs caught”
would overstate both tools.

## Comparative result

| Dimension | RBS / Steep | Sorbet |
| --- | --- | --- |
| Signature location | External `sig/*.rbs`; implementation stays quieter | Inline and local, but materially enlarges classes |
| Strongest result in rush | Precise static graph and boundary ledger; recursive unions and structural protocols | Independent class/dispatch model plus optional nominal runtime call checks |
| Gradual-typing metric | Typed calls, determined mainly by receiver type | Typed sends/usages over a different configured input set |
| Best design pressure | Make collaborators, tuples, and invariants explicit | Make call shapes, returns, and runtime classes explicit |
| Major ecosystem failure | Duplicate stdlib extension silently poisoned a whole class to `untyped`; `Data.define` attribution/crashes | Incorrect/loose stdlib RBIs; wrapper loaded unrelated broken gem RBI |
| Dynamic Ruby friction | Frozen callable registries, repeated-call narrowing, Racc/generated code | Non-static splats, literal narrowing, generated superclass visibility |
| Runtime effect | None | Optional validation; approximately 2× interpreter-workload cost here |
| Main maintenance cost | 7,801-line parallel signature tree and boundary augmentations | 1,504 inline declarations, RBI shims, runtime dependency, metric noise |
| Current residual ledger | Generated Racc parser; 18 untyped calls in two files | Generated parser ignored; five production files remain `typed: false` |

Steep was the better primary static checker for rush by the criteria this project needed: a detailed
external domain model, an explicit receiver-based boundary ledger, and no runtime tax. Sorbet was
the better adversarial second checker because it disagreed at different seams and could turn
signatures into runtime assertions.
That is not the same as saying Sorbet was weaker in general, or that every Ruby codebase should
prefer RBS. It is the result for an AST-heavy interpreter with metaprogrammed value classes,
generated parser code, syscall boundaries, and a very hot internal dispatch loop.

## Recommendations from the experiment

If adopting one gradual type system:

1. **Measure the untyped surface, not just command success.** A green checker with an accidentally
   untyped library class is worse than an explicit ignore.
2. **Type high-fan-out collaborators first.** Receiver precision propagates farther than polishing
   isolated leaves.
3. **Prefer structural invariants to casts.** Treat every silent coercion as a transferred proof
   obligation.
4. **Keep a boundary ledger.** Generated code, native calls, dynamic registries, and intentionally
   open payloads should be named, not dissolved into a project-wide `untyped` baseline.
5. **Run the full quality gate after type fixes.** A checker-approved shape may still be duplicated,
   over-complex, behaviour-changing, or untestable.
6. **Profile runtime validation in the real workload.** Do not infer its cost from startup or a
   microbenchmark.

If running two systems:

1. keep the signature sets independent enough to disagree;
2. make the inter-DSL bridge deliberately opaque rather than translating types;
3. do not compare incompatible coverage percentages as a leaderboard;
4. expect class shape and library stubs — not primitive application types — to dominate the
   disagreement;
5. budget explicitly for duplicate declarations and two ecosystems' defects;
6. stop when the second system only mirrors the first. Its value is the drift catalogue, not the
   second green checkmark.

## Reproducing the static measurements

The normal gates are:

```sh
bundle exec rake steep
bundle exec rake sorbet
bundle exec rake
```

Steep's call ledger can be aggregated from:

```sh
bundle exec steep stats --format=csv
```

The runtime-cost experiment recorded in
[`e2b9cc1`](https://github.com/tank-bohr/rush/commit/e2b9cc1359b60e90c7689ddad1d7211463c92f9e)
uses the committed `while_arithmetic` and `expansion_heavy` workloads, five samples after one warmup,
and can be rerun in unchecked and checked modes with:

```sh
RUSH_BENCH_SAMPLES=5 bundle exec rake benchmark
RUSH_RUNTIME_TYPECHECKS=1 RUSH_BENCH_SAMPLES=5 bundle exec rake benchmark
bundle exec rake benchmark:profile
RUSH_RUNTIME_TYPECHECKS=1 bundle exec rake benchmark:profile
```

Sorbet's counter scope can be inspected with the same raw binary used by the rake task:

```sh
bin=$(bundle exec ruby -e \
  's=Gem::Specification.find_by_name("sorbet-static"); print File.join(s.full_gem_path,"libexec","sorbet")')
"$bin" --track-untyped --counters
```
